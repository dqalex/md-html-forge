# 产品定位

> 本文档是 md-html-forge 的产品真相源。所有技术决策、组件设计、文档规范都必须服务于这里定义的产品方向。
>
> 最后更新：2026-05-10

## 一句话定位

**「Claude 输出的最佳渲染器」** — AI 完成 99% 的内容创作，用户手改 1%。

## 核心价值主张

### 为什么是"渲染引擎"而不是"HTML 编辑器"

省 AI token。AI 只产出符合规范的 Markdown，不需要生成冗长的 HTML。

### 为什么兼容 Markdown

MD 是成熟标准，有大量存量用户和工具链：

- 存量用户零学习成本接入
- 源文件在任何 MD 编辑器打开都可读
- AI 天然熟悉 MD 语法

### 为什么需要用户手改

AI 多轮对话效率低。如果 AI 已经完成 99% 的工作，用户通过对话让 AI 改最后 1%，很可能要多轮才能 get 到用户改的具体是什么。让用户直接动手改更快。

**手改覆盖两个层次，缺一不可**：

| 层次 | 内容 | 典型场景 |
|---|---|---|
| 内容层 | MD 文本里的词句、数字、标点 | 改一个错字、调一个数据、换一个措辞 |
| 审美层 | 组件变体、字体、配色、主题 | 同一段内容换一种展示方式 |

### 为什么渲染出的 HTML 必须可交互

这是本产品相对于前置项目（teamclaw）的关键差异化。

- **交互是 HTML 的核心价值**。把 AI 产出渲染成静态 HTML 等于降级——浏览器的长处没用上
- **双向同步**是产品体验闭环：用户在预览里点击、编辑、拖拽，变化自动回写 MD；用户改 MD，预览的交互态同步更新
- 源 HTML（如 `html-effectiveness` 的模板）本身带 JS 交互，如果我们的引擎不支持，渲染出的结果就是阉割版

## 产品生态位

用户完成工作流的**中间件**：

```
  ┌──────────────┐     ┌──────────────┐     ┌──────────────┐     ┌──────────────┐
  │ AI 按规范产出 │────▶│ 本产品自动匹配│────▶│  用户双向微调 │────▶│ 对外发布/存档 │
  │   Markdown   │     │  组件并渲染   │     │ 内容 + 审美   │     │   保持一致性  │
  └──────────────┘     └──────────────┘     └──────────────┘     └──────────────┘
        上游                 本产品                审美层               下游
```

- **上游**：AI 根据我们的规范产出 Markdown 文档
- **本产品**：MD 进入 → 自动匹配组件 + 渲染（含交互）→ 用户双向微调（内容 + 审美）→ 可保存为品牌包
- **下游**：对外发布，**保证内容一致性**（主要服务商务场景）

## 核心用户场景

商务用户：需要持续对外发布内容（周报、PR 总结、事故复盘、产品说明），希望：

- 同一类文档**每次发布的视觉风格一致**
- 允许品牌化定制（品牌 logo、专属配色）
- 输出的文档是**活的** — 读者可以交互（勾选、折叠、对比）

## 产品护城河

不是 91 个组件本身，而是：

1. **一份给 AI 的规范**（`forge.md`）— 决定 AI 怎么写、组件库长什么样、主题怎么组合
2. **组件变体系统** — 同一概念多种长相，用户点击切换
3. **组件包格式**（`.forge.md`）— 用户/AI 可自定义组件，四件套（slots + html + css + js）放在一个 md 文件里，可导入、可分发
4. **双向交互同步引擎** — 预览可交互、改动自动回写 MD
5. **渲染配方保存机制**（品牌包）— 用户沉淀的审美选择可复用

## 开源与变现策略

- **完整开源**：整个渲染引擎、组件库、组件包格式、规范都开源
  - 理由：渲染管线的思路已经在 teamclaw 开源过；模板组件取自另一开源项目；本项目顺承同样的开放姿态
- **变现路径：API 服务**
  - 面向不想自己部署/维护的用户，提供线上渲染 API + CLI
  - 面向企业，提供多品牌管理、批量渲染、私有部署
- **不做**：组件库付费解锁、模板市场抽成、付费主题包 — 所有开箱能力完全开源免费
